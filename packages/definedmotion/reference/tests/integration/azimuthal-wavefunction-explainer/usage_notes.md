# Azimuthal wavefunction explainer usage notes

These notes record the experience of reproducing the supplied vertical orbital/azimuthal animation as a horizontal DefinedMotion explainer. The reference establishes the conceptual sequence and cyan-on-black scientific character; the composition is rebuilt for a 1280×720 blackboard presentation rather than copied frame-for-frame.

## Authoring intent

- Preserve the progression from a rotating probability cloud, through real orbital shapes, to the separated azimuthal factor and its polar modes.
- Use the horizontal frame for relationships: compare `s`, `p`, and `d` orbitals in one row, then place the polar diagram beside the matching cosine trace.
- Keep typography camera-attached and minimal, with no decorative panels.
- Make every stochastic-looking cloud deterministic so reloading or scrubbing directly to a frame gives the same result.

## Initial observations

- DefinedMotion does not need a particle-system primitive for a fixed probability cloud: a deterministic `THREE.Points` geometry is compact and rotates cheaply. The important authoring rule is to derive rotation from the global frame rather than accumulating it per tick.
- The live polar and cosine diagrams need changing thick curves. Core Three.js line width is not portable across renderers, so the first scene version required custom dynamic ribbon meshes. That experience produced the measured `createCurve` primitive: the scene now supplies only `pointAt` and `visibleAt` mathematics while the library owns ribbon geometry, dashes, buffer reuse, and bounds.
- A horizontal adaptation is not a crop of the vertical reference. The three orbital examples and the final integer modes become rows, while the live polar/wave comparison becomes a two-column relationship.
- The first build overfilled two beat windows because a long camera animation had already advanced the local authoring pointer before a wait was added. `ANIMATION_OUTSIDE_BEAT` identified the exact global animation and beat ranges before any frames rendered. The guard is effective; authors still need to remember that every `addAnims()` call advances the pointer by the longest parallel plan in that call.
- The first all-frame trace found the marked separation equation two pixels outside the safe area and the rotating sphere/axes too low during an intermediate camera frame. A slightly smaller equation and an authored upward offset on the complete sphere construction fixed the hierarchy at its source; no verification margin was relaxed.
- The first timeline grid revealed brief black gaps because outgoing and incoming beats were authored as sequential fades. Rewriting them as parallel crossfades made the global transition continuous and also simplified each beat's pointer arithmetic. The same grid showed that a literal scale translation from the vertical source wasted the horizontal frame, so the cloud, orbital row, live two-column diagram, and final mode row now use independently chosen authored scales.
- The larger separation sphere could not be revealed during the camera move: even at near-zero opacity it had real projected bounds in a camera pose authored for the orbital row. The transition now keeps the old construction visible while the camera moves, then crossfades at the destination pose. This is clearer than teaching verification to ignore low-opacity geometry and avoids both black frames and invalid intermediate composition.
- Generic collision watching was a poor fit for this composition. The quiet full-frame point field overlaps every camera-attached label by construction, while deliberate crossfades briefly put consecutive titles and formulas in the same band. Rather than add broad ignore lists that make the watches appear useful, the scene uses authored verifications for the actual contracts: typography stays inside its bands, world visuals remain between those bands, and the final mode diagrams stay separated.
- The first orbital captions were manually positioned text and LaTeX, which produced a cramped result despite reasonable-looking coordinates. Replacing each pair with a fit-content `layout.flex` column made the relationship explicit and produced a stable measured gap. The five camera title/equation pairs now also use fixed-height flex columns with `space-between`, so their bands are owned by one layout rather than two unrelated positions.
- Layout centering is local to the visual plane. During an oblique camera move, perspective projection can shift the screen-space centers of two correctly centered children by different amounts. A verification that demanded identical projected centers was therefore wrong; the durable checks are that the layout owns both children, contains their bounds, and preserves a readable projected gap.
- Consecutive camera layouts should not crossfade their text in the same slots: even correct layouts become illegible when two titles or equations overlap. The scene now uses `getTimelinePointer()` and `setTimelinePointer()` to sequence the overlay fade-out/fade-in while the world geometry and camera continue their parallel transition.
- Simple two-point axes use `createLine`, and all polar and Cartesian mode paths use `createCurve`. Probability clouds, arrowheads, and wire spheres remain direct Three.js geometry because the current DefinedMotion primitives do not represent those constructions.
- Migrating the scene confirmed that `setPath()` is the right escape hatch for mathematically exact procedural motion. Interpolating only between integer path snapshots would not reproduce the true intermediate non-integer modes; `onEachTick` evaluates the actual mode and updates four reusable curve buffers instead.
- The complete orbital comparison, live polar/wave pair, and final integer-mode row deliberately retain explicit positions. These are fixed world-space diagrams where equal authored centers communicate the comparison more directly than responsive bounding-box spacing; layout remains responsible for their variable-size captions and camera typography.
- Trying automatic layout for the orbital row clarified an important boundary: layout intentionally excludes an item's root animation transform from intrinsic measurement. Moving the authored `1.2` scale into a descendant content group made it measurable, but added structure without improving this fixed composition, so explicit centers were the clearer choice.
- Planar curve plots work with ordinary local-Z separation once opaque curve ribbons write depth. The live polar/wave plots and final mode plots now place their data a small distance in front of their axes; no material traversal, disabled depth testing, or explicit render order is needed.

## Validation log

- The exact 2,220-frame trace passes all 10 authored verifications (8,464 executed checks), including the new all-orbital-beat layout contract.
- Two timeline grids were reviewed: a 12-frame transition grid and a larger six-keyframe grid. They confirmed continuous crossfades, readable horizontal relationships, deterministic direct-frame rendering, and the intended non-closing `m=2.5` mode.
- The repository test gate passes: TypeScript, Svelte diagnostics, unit contracts, documentation validation, and generated-reference import validation.
- `layout-check` intentionally reports `NO_COLLISION_WATCHES`. This scene uses the authored all-frame verifications above instead of generic watches whose only incidents were the decorative point field and deliberate overlay crossfades.
